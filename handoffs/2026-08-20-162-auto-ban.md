## What it does

lg-login-monitor's credential-stuffing detector — 5 distinct REAL accounts
failing from one address inside 15 minutes, the same threshold that already
sends Ian an email — fires `do_action('lg_login_stuffing_detected')` at the
moment it alerts. `lg-auto-ban.php` records the offender; a root path-watcher
plus a 5-minute timer rebuild an nginx deny list; nginx refuses that address at
the login door for 24 hours and shows it a polite page.

Ian's narrowing (8/20, verbatim): *"this should only block ips that try several
different logins in one block."* Nothing else bans anyone — 50 attempts against
one account does not, and gate 84 §B2 asserts it.

## The two things that reshaped the ruled design

**1. Neither box restores real client IPs.** No `set_real_ip_from` anywhere in
`/etc/nginx`; the access log's last five requests came from `104.23.190.196` and
`162.158.159.108`. `$remote_addr` is a Cloudflare edge node, so the obvious deny
would ban the edge and take the whole site off the internet for everyone behind
it. Enforcement keys on `CF-Connecting-IP` behind a `geo` vouching block instead.
Adding `set_real_ip_from` globally would silently re-point access logs, the
`/thumb/` `limit_req` zone and the `allow 127.0.0.1` lock on
`/wp-json/looth-internal/` — its own issue, not a side effect of this one.

**2. That header is forgeable, and the origin is world-knockable.**
`lg_login_monitor_client_ip()` honours it unconditionally. Fine for decorating an
email; as a ban trigger it means anyone could connect straight to the origin,
forge the header, fail five logins against five real member logins, and put an
address **of their choosing** on our blocklist. `lg_ab_vouched_ip()` is a separate
computation: believe the header only from a Cloudflare range, otherwise ban the
real peer. Proven end to end — same request, same forged header, the only
difference being whether the connection is vouched (gate 84 §G8/§G8b).

2. `ln -s` `lg-auto-ban.php` into the docroot **in the same window** — mu-plugins

## Gate 84 — 68 assertions, and what it found

Runs the real mu-plugins against a stubbed WordPress and the real generated nginx
config on a throwaway unprivileged nginx, per-run temp dir and per-run port. No
network, no root, no DB, no WordPress, no FPM. The door points at a socket that
does not exist, so 403 = refused and 502 = reached the hand-off to PHP.

Red-first: 34 mutations each reddening its OWN named assertion, 4 no-ops proven
inert, on snapshots and never `git checkout --`.

**Three real defects, all found by the gate, all fixed:**

1. **The renderer could not be told not to touch nginx.** An empty env value read
   as "unset", so every offline render still shelled out to the real `nginx -t`,
   failed as a non-root caller and rolled its own work back. Six assertions went
   red for a reason none of them was about.
2. **The generated conf carried its own render time**, so its bytes differed on
   every run — the 5-minute expiry timer would have `nginx -t`'d and reloaded
   nginx **forever, on a box with no bans on it**. Found by a *no-op* mutation
   reddening the idempotence leg. Everything clock-shaped now lives in the status
   file; §D7b asserts it can't come back.
3. **§C3 was passing for the wrong reason.** Its fixture peer is itself a
   Cloudflare address, so the structural refusal caught the case whatever
   `lg_ab_vouched_ip()` returned — the rule could be deleted outright and the
   assertion stayed green. §C3b now asks the function directly.

## Known gaps, stated

- An attacker connecting direct to the origin and **rotating** a forged
  `CF-Connecting-IP` evades *detection* — the detector keys its per-IP set on the
  forgeable address. Pre-existing, and unchanged here by ruling ("same threshold,
  no new detection"). Worth its own issue.
- `?rest_route=` is an alternate spelling of a REST path and would not match the
  exact `location` on the membership auth door. That door keeps its own
  6-per-email / 21-per-IP-per-hour 429 throttle either way.
- PHP's `FILTER_FLAG_NO_RES_RANGE` and Python's `ipaddress` disagree about RFC
  5737 documentation ranges. The renderer is stricter and is the authority; it is
  also why the gate's fixtures use real-shaped addresses.
- dev2 cannot prove enforcement against a real browser: every request arrives
  through the same Cloudflare edge and the dev gate sits in front of everything.
  The gate proves the generated config behaviourally; the live proof is Ian's own
  browser after step 6.

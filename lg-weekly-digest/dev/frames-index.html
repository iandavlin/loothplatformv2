“Your week” — the shipping design

Real frames of the real email: the actual lg-weekly-digest issue of July 13 rendered through the shipping builder, with the recap section fed real rows out of profile_app.notifications and message_recipients. Nothing here is a drawing. Phone 390px left, desktop 720px right.

Updated 2026-07-27 after Ian’s call. He picked the recommended design, so the alternatives are gone — from this deck, from the spec, and from the renderer, which no longer has knobs for them. The section is now personalised with the member’s profile name.

Two dev2 artefacts to ignore, neither is in the email: nginx injects the site’s PWA bottom-nav into every HTML page on this box (the frames are sandboxed so you won’t see it, but you will if you open a frame directly), and the curated sections’ images are broken here because their thumbnails sit behind the dev gate.

What was decided closed

Recorded so nobody re-opens it. The rejected shapes are not options in the code — there is no flag to flip. They survive only as history in docs/atlas/WEEKLY-DIGEST-RECAP.md §4.

Discussion titles are named.

“2 new replies on your discussion — “Suggest an alternative to concave fret file” — Doug Proper and 1 other.” A public forum title is already public; it is not message content, which is what the ruling forbids.

Every row carries its own deep link.

The mention opens that reply in the discussion modal, the reaction opens that post, the DM opens the sender’s profile. The links already existed — the notification bridge stamped a canonical /hub/?topic=…&reply=… on each row when the event fired.

The section sits at the top, under the intro rule.

It is the only part of the email about them, and it is three or four lines.

It greets the member by their profile name.

First token only — “Here’s your week, Dave.” — which is not a new convention but the one the front feed already uses (archive-poc/web/index.php:504-518, “Welcome back, <first>.”). That code carries the reason: the legacy name system backfilled business names into profile display_name, so the first word is the only token reliably the person. The name comes from profile_app.users.display_name — the same row /u/ renders — never user_login, never a Patreon handle. No name on file → no name in the greeting, same as the front feed. (For the record: 0 of 1,851 live profiles have an empty display_name and 0 have a bare Patreon handle in it.)

Reactions are in, batched; the section caps at 8 rows.

One row per thing reacted to. A busy week rolls the tail into “N more updates waiting for you” rather than running long or truncating silently.

What the notification store does and does not know

The audit that briefed this lane is a month stale in the one way that mattered most. Correcting it here because the next person will read the audit and assume less.

  • It knows more than NOTIFICATIONS-AUDIT.md says. That audit (2026-06-27) records the bell as connection-request/accept only. Since 2026-07-12 it also carries forum.reply_to_topic, forum.reply_to_reply, forum.mention and reaction.on_post — written by lg-shared/notify-bridge.php, with an actor, a coalesced actor_count (“and 2 others”), and a stamped canonical deep link. That last one is why this section did not need a query layer over forums.*: the links already exist.
  • It still does not know about DMs, on purpose. profile-app deliberately does not ring the bell for a new message (“no double-notify”), so unread DMs are read separately from message_recipients.unread_count and merged in.
  • There is no URL that opens a DM thread. The messages surface is a modal opened from the header button; social-modals.js reads no query param and no hash. So a DM row points at the sender’s profile instead of inventing a link that lands nowhere. A ?dm=<thread-uuid> trigger would be small and would follow the pattern #search and ?compose=1 already set — but it is a Hub change, not a digest change, so it is flagged rather than done here.
  • WordPress cannot read the store. The WP pool runs as looth-dev, which has zero grants on the profile_app database — the same reason the bridge POSTs over loopback rather than writing PG. The send-time reader is therefore a loopback endpoint, mirroring the existing writer.
  • The per-recipient mechanism works. A custom smart code registered through FluentCrmApi('extender')->addSmartCode() substitutes per subscriber at send, and a raw_html campaign — which is what the digest sends — bypasses FluentCRM’s per-campaign body cache, so each recipient gets their own render from one campaign. Trap for later: moving the digest onto a block template would silently bake one member’s recap into everyone’s email.

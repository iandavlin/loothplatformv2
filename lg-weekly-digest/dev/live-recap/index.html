What is real, and what is not

real The recap data. Live POST to https://127.0.0.1/profile-api/v0/internal/recap on dev2, authenticated with /etc/lg-internal-secret, hitting the profile-app FPM pool and the real profile_app Postgres store. No lg_wd_recap_fetch filter was installed, so LG_WD_Recap_Source::post() made the real call. source_answered() was true for every member — so an empty section here means a quiet week, not a dead endpoint.
real The FluentCRM substitution. FluentCrm\App\Services\Libs\Parser\Parser::parse($body, $subscriber) — the exact call CampaignEmail::getEmailBody() applies to each recipient row at send. The smart code was registered through the real FluentCrmApi('extender')->addSmartCode() path. These are real FluentCRM subscriber records.
real The email body. Rendered by the deployed LG_WD_Email_Builder::build($payload, ['mode' => 'token']) from a real weekly_email issue, with the token emitted by the real templates/email.php. The lane’s recap files were diffed against the deployed plugin and are byte-identical — this is the shipping code.
not real The flag. LG_WD_RECAP_ENABLED is OFF on dev2 and was not changed — it was turned on for the lifetime of one CLI process via the lg_wd_recap_enabled filter, so nothing about this box was left armed.

Turning it on does NOT auto-mail anyone (corrected 2026-07-31 after Ian said he never runs the digest on cron). Verified against live’s own stored settings, read-only, not from recollection: live has enabled = false, so LG_WD_Cron::fire() logs and returns at class-lg-wd-cron.php:31 before doing anything; and cron_mode = draft_and_notify, so even with that brake released it would create a draft and email one admin a review link (class-lg-wd-cron.php:67) rather than call the sender. On top of that, LG_WD_Sender::send_issue() finishes by setting $campaign->status = 'draft' (class-lg-wd-sender.php:237) — the plugin never dispatches; Ian reviews and sends from FluentCRM.

What the flag does change is worth being deliberate about: when the next issue is built through the plugin, recipients_with_something_waiting() runs at campaign-creation time (class-lg-wd-sender.php:200) and decides who gets a CampaignEmail row. That is visible before sending — the result reads “Campaign created with N subscribers”, so a surprising N is the check to make in FluentCRM before pressing send.
not real The send. Nothing was sent, queued or scheduled. No campaign, no CampaignEmail rows, no wp_mail. Bodies were rendered to disk. dev2’s mail is swallowed by mailpit, which returns success — so a send here would have proved nothing anyway.
not exercised Click tracking on recap links. Known and accepted: FluentCRM caches the click-tracking URL map per campaign, so per-recipient recap links are not tracked. The links themselves are correct. Documented in class-lg-wd-recap-source.php.

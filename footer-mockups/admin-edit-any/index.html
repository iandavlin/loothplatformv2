Edit any post as admin

Ian, 7/30: “I need to be able to edit any post as admin as well. Full functionality on any post editing as admin.” This page is the decision, not the build — nothing has been built yet. The short version: the front-end composer this ask assumes only exists for discussions. Video, article, event, loothprint and sponsor have no front-end create or edit form at all. So there are three real shapes this can take, and they are days, weeks and “a bit of both” apart.

View as

Flip this. On every drawing below, the Edit control has to vanish — on someone else’s post, on every type, on both viewports. That absence is the part I’ll be gating.

Option A — the Edit button reaches the editor that already has every control Recommended · days

An Edit control on every post — hub cards and the standalone pages — shown only to someone who genuinely may edit that particular post. It opens the real editor the post was made in. “Full functionality” isn’t approximated here, it’s guaranteed: it’s literally the same editor, with all 7–28 of that type’s controls. And it adds no new save path, so the content-destroying bugs we fixed yesterday can’t come back through it.

The honest cost: that editor is wp-admin, not the front end. This is the fastest route from “Ian is looking at a bad post” to “Ian has fixed it”, on every type, this week — but it is not the front-end composer, and I’m not going to call it one.

Option C — a front-end quick-edit for the common fields I’d argue against · ~1 week

A real front-end sheet on every type, but only the fields every type shares — title, excerpt, cover, tags, tier, status — with “Open the full editor” for the rest. It is genuinely front-end, and it covers the everyday admin fix.

Why I’d still not build it. It needs a brand-new write endpoint for content posts — which is exactly what re-opens the content-destruction failure class we just spent yesterday closing on discussions. And it is explicitly not “full functionality”, which is the phrase you used. It buys the least per unit of risk of the three. I’m drawing it because it’s the obvious middle and I don’t want it picked by accident.

One thing worth knowing before you decide. WordPress still holds a full set of front-end “Add / Edit your Loothprint / Video / Article…” pages from the old theme — on paper, this whole feature, already built. They’re dead: their forms were Elementor widgets, and Elementor was switched off when we moved to the current theme, on both boxes. I loaded one as you and as an ordinary member: the instructions render, the form has zero fields. Turning Elementor back on to resurrect them would be a bigger and riskier change than Option A, and it would drag seventeen pages of stale layout back into the live theme with it.

Whoever gets this button — the bit I want signed off

The obvious way to gate it is the flag every existing Edit button already uses. That flag means “forum moderator”, and a forum moderator is not someone WordPress lets edit an article. Reusing it would quietly hand every moderator edit rights over the whole content library:

If we gate on…You (admin)A forum moderatorAn ordinary member
the existing moderator flagedits everythingedits everything ✗own posts only

Nobody is over-granted today — there are no forum moderators on either box right now, so this is one role assignment away from mattering rather than a live hole. The second row is what I’d build, and the server would re-check it on every save regardless of what the button shows.

What I need from you

A, C, or B. My recommendation is A now — behind a flag, off by default, so it reaches the box harmlessly and you can click the real thing before it’s switched on — and treat B as the front-end-authoring program it already is on the backlog, phased by you. If A is too much of a compromise, say so and I’ll size B properly instead of starting it sideways.

Nothing real is lost at 6. The most photos on any published reply in the forum's history is five. The two rows in the store that hold 10 and 11 are orphaned attachments from a previous lane's test — they have no reply attached to them any more. So the cap costs zero existing content, and the +N affordance below exists purely so that if one ever does turn up it is shown rather than silently dropped, the way LIMIT 1 has been dropping them.

One fetch

The replies fragment serves five stubs at a time ($PER = 5, then “Load 5 more”), so five image-carrying replies is the real payload unit — not one. Here they carry 6, 3, 2, 5 and 4.

Every tile is loading="lazy" with intrinsic width/height, and asks the resizer for a tile-sized image instead of the w=800 the old single image always pulled. Measured on real photos: 11.6 KB at w=240 and 35.8 KB at w=480, against 79 KB for the w=800 the hub used to fetch for a thumbnail. Six tiles now can cost less than one image did.

The cap at the door piece two

Six is enforced, not decorated. One constant, four places that honour it.

WhereWhat it doesBites today?
bb-mirror/config.phpLG_REPLY_IMG_MAX = 6 — the single source; renderer and endpoint both read it, so they cannot drift—
reply.php POST422 too_many_media before the insertYes — composer v2 posts creates here
reply.php PUT422 on the resulting set (kept + newly added), so an edit can't walk a reply past the cap one photo at a timeYes — all edits go here
Composer v2 (lgcUploadPhoto)refuses past 6, disables the photo button, and shows a live “3 of 6” count so the cap is visible before it is hitYes
Legacy desktop trayssame guard via lgComposerTray({max:6})Yes — interim, see below
auth.phpships the number to the client, so the composer's guard and the server's 422 are the same 6—

The one honest gap. The legacy desktop reply composers still POST BuddyBoss REST direct on create, so reply.php's 422 never sees them and their client guard is all that holds the cap there. composer-p3 deletes exactly those paths (W1/W5); once it lands the server is the backstop everywhere. Until then the guard is real but client-side on that one surface — which is why it was added rather than left to p3.

The count is taken from the chips in the strip, not from the uploaded-ids array — so a photo that is still uploading, one that failed and is waiting on a ↻, and an existing photo kept on an edit each occupy a slot, exactly as they appear to the member. Topic composing is not capped; this is a reply cap.

Status

What is proven and what is not.

Verified — 36 assertions green (footer-mockups/reply-images/verify.sh), run against the live mirror through the real renderer:

  • a single-image reply renders byte-identically to the pre-change code — diffed against the renderer pulled out of git, not eyeballed
  • 2–6 produce the right cell count; 1 produces no gallery at all
  • every tile carries srcset (3 candidates), sizes, intrinsic width/height and loading=lazy
  • sizes tracks the span rule — half-width layouts declare half-width, and no layout declares the other one
  • an over-cap reply shows six tiles and a +5
  • both server caps sit before the writes they guard, and the PUT cap counts the resulting set

Not yet proven — needs a serve window and a real device: the 422 exercised by an actual over-cap request, the composer guard and “3 of 6” read-out driven by a real finger, and the gallery on Ian's phone. A green harness has lost to that phone three times this week; this deck is not a substitute for it.
